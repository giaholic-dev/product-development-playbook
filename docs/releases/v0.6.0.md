This release consolidates material integrated work since published v0.1.0 (`d5282751d8568e9fc70262daf9751687c3fec8a2`), including the delivery boundaries previously accepted as v0.2.0–v0.5.0. ## Material changes since v0.1.0

### Complete lifecycle and repository governance

- Seven maintained lifecycle documents now cover Foundation through Maintenance, with Product, UX, Architecture, Development, Release and Maintenance guidance and their governing standards.
- Repository workflow, readiness, review, completion, issue/PR templates, automation, documentation responsibilities, terminology and artifact standards establish traceable evidence and decision boundaries.
- Standards Index, relationship map, glossary and artifact catalog improve discovery. The glossary indexes primary definition owners; the catalog does not introduce extra mandatory deliverables.
- Work classification separates Phase, Work Type, optional artifact category, Priority, provider Issue Type and workflow status. Every work item retains one primary Phase and Work Type. Documented equivalent representations remain possible outside an adopted GitHub Project mapping; the adopted Project mapping requires actual Phase and Work Type fields.

### Execution and integration boundaries

- Work Management, Roles and Actor Assignment, Execution Protocol and the Master Execution Checklist distinguish work decisions, scoped responsibility/Authority, execution attempts and navigation.
- The checklist indexes all 33 current lifecycle activities and links their owners, with a reusable record and fictional walkthrough. Checklist completion is not proof of product execution or approval.
- Integration contracts and provider implementation guidance separate conceptual needs from native provider support, current connection capabilities, authorization and verified outcomes. Unavailable tooling preserves an unmet obligation or a governed fallback.
- Manual, AI-assisted and authorized automated execution use the same governance. No AI provider, machine schema, parser, runtime or automatic state-transition model is required or established.

### Product-type architecture boundary

- Product Type, Context and Composition, core/specialization boundaries and Standards Applicability now support explicit source-level contextual assessment.
- The seven-phase/33-activity assessment compares software, physical, service and hybrid conceptual scenarios, preserving uncertain or incompatible gates.
- Existing software adoption remains the supported operational scope. This architecture does not publish manufacturing, service-production or hybrid specialization methods, a universal lifecycle, or empirical non-software validation.

### Environments, promotion and upgrades

- Executable or served software products require three existing, distinct Development, Test and Production environments with verified isolation before implementation work under Development. Small size, static hosting, manual deployment and free tiers do not waive this requirement.
- The same identified candidate progresses through Test to Production with recorded configuration differences, scoped production approval and post-deployment verification/recovery evidence.
- Runtime application identities remain separate from authorized deployment-task identities. Scoped production deployment access does not grant ordinary Development/Test runtimes production access or supply promotion approval.
- Three full-lifecycle examples, six checklist references and an optional Software Environment Record illustrate preparation, isolation, promotion and failed verification. They are fictional demonstrations, not provisioned environments.
- Conformance declarations now identify an immutable adopted baseline and distinguish released from unreleased sources. The upgrade procedure records changed obligations, remediation, exceptions and accountable decisions.
- A methodology-only repository's utilities/CI do not themselves create a runtime product; served documentation products remain in scope.

### Supporting tooling and fixes

- The optional Bash audit exporter creates a timestamped offline package, collects the currently implemented GitHub records, validates declared counts/identity relationships, applies owner-only output permissions and rejects failed/colliding exports.
- Timeline handling preserves distinct ID-less events and scopes provider IDs by issue and event kind; only identical observed ID-less payloads are deduplicated.
- The audit-comment regression assertion now checks jq's exit status. A negative empty fixture must fail with false-result status 1; malformed input is not accepted as a successful negative test.
- Python-standard-library documentation validation and a read-only GitHub Actions workflow check supported local links and heading fragments. Seven behavioral tests cover failure and example cases. Python 3.12 or later is required.
- Optional Codespaces configuration, shell conventions, fixtures and CI support maintainers without becoming product-runtime requirements.

## Adopter actions and compatibility

1. Preserve the previous baseline and evidence. Resolve v0.6.0 to its immutable tagged commit and record the source, assessment date, owner and reassessment condition.
2. Compare changed governing sources with the previous adopted revision. Apply each source's scope and strength; a new label or pulled update does not establish conformance.
3. For executable/served products, assess the actual three environments, isolation, credentials, data/integration effects and same-candidate promotion. Record gaps and accountable remediation; further Production promotion follows the standard or its governed exception treatment.
4. Verify the selected tracking representation. Within an adopted GitHub Project, update actual Phase/Work Type values; an issue-body edit does not update fields.
5. Use [Playbook Upgrade Guide](../practices/playbook-upgrade-guide.md) and [Conformance Declaration](../../templates/conformance-declaration.md) to record the adoption decision, completed work, unresolved obligations and any permitted exceptions.

No files are removed by the reviewed v0.1.0-to-candidate comparison. The larger governing baseline can introduce obligations for an adopter; version numbering does not waive their assessment.

## Known limits and excluded work

- The current exporter does not provide a complete declared source snapshot: it copies selected documentation/configuration, while the tree listing is not the missing source bytes. Scripts, .github and .devcontainer source coverage requires the later approved coverage contract.
- PR conversation comments and review submissions are not fully exported by the current collectors. Inline review comments do not establish complete review or approval history.
- Project item field values are not exported by the current item query. Field definitions and item metadata do not establish actual Phase, Work Type or other planning values.
- Manifest pagination/count checks cover the implemented collectors; they do not prove coverage of absent collections or an atomic provider snapshot. A successful package is not a comprehensive audit/conformance certificate. See A01–A06 in the [remediation plan](../practices/playbook-remediation-plan.md).
- New persistent-state recovery/migration rules remain O01–O04 research-dependent work. Existing rollback guidance must not be read as proof of backup restoration.
- Machine-execution representation remains deferred. Non-software specialization/pilot, product retirement and empirical reading-usability research remain unversioned candidates.
- Documentation validation covers the [README parser contract](../../README.md#documentation-checks), not semantic correctness, external URL availability, complete navigation or product conformance.
- Project legacy optional artifact metadata and all historical controls/approvals are not exhaustively certified. This release verifies the 25 remediation issues' mandatory fields, not every historic provider record.

## Support and recovery

Report a concrete defect through a [repository issue](https://github.com/giaholic-dev/product-development-playbook/issues), identifying the adopted commit, affected source and evidence. The maintainer @giaholic owns release follow-up.

Keep the previous immutable baseline and adoption records. If an upgrade is unsuitable, pin the prior baseline and record the accountable disposition and affected obligations; do not rewrite the published tag or claim the newer requirements were met. A material release correction uses a traceable follow-up change/release. This is a methodology-content recovery path, not a production-data restoration procedure.
