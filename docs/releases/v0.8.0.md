## Adopter upgrade actions

1. Preserve the prior immutable baseline, actual observations and decisions. Compare the changed clauses with the selected product/constituent; version numbering alone proves no conformance. Use the [upgrade guide](../practices/playbook-upgrade-guide.md).
2. Identify material state and authoritative/reconstruction inputs, including devices, files, queues and managed providers. Record evidence-backed stateless inapplicability, or explicit uncertainty/gaps; lack of a self-managed database is insufficient.
3. For affected stateful releases, select proportionate point/loss/time boundaries and method, then establish representative restoration/compatibility and migration/failure/retry evidence with data protection and authorized operators. Record incomplete evidence, accountable remediation or an exception only under the governing source's permission.
4. Assess later legitimate writes, irreversible transformations, delayed consumers and external effects. Do not claim that redeploying old software restores compatible state or reverses lost/changed data. Preserve failed/inconclusive outcomes and reassess before future dependent exposure.
5. Record the accountable upgrade decision and follow-up. Do not invent historical restore tests or use the fictional walkthrough as execution evidence. Stateless scope retains source/artifact/configuration recovery and applicable environment/promotion obligations.

Existing architecture, decision, deployment or incident records can contain the evidence. No particular database, paid service, backup tool, exercise frequency, numerical objective or new file is mandated. A methodology baseline change does not undo an adopter's real data migrations or erase prior obligations/accepted risk.
